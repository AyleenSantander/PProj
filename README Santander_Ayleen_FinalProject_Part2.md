## Part 1: Integrating Data from an API

### `01\_fetch\_tickets.py`

1. **Pagination (item 1):** follows `meta.next` from each response rather than hard-coding a page count, so the script keeps working if the feed grows.
2. **Rate limiting (item 2):** on an HTTP 429, reads the `Retry-After` header, sleeps that many seconds, and retries the same page — it never skips a page or crashes on a 429.
3. **Optional fields (item 3):**

   * `resolution\_days` is `NULL` for open tickets, not `0` — a ticket that hasn't been resolved yet has no resolution time to report, and `0` would falsely read as "resolved instantly."
   * `satisfaction\_score` is likewise `NULL` for anything but resolved tickets, for the same reason: absence of a survey response is not the same as a score of zero.
4. Writes every fetched ticket to a **staging table** (`support\_ticket\_staging`, all columns text-typed, matching the Project 1 stage-first pattern) before anything is typed or matched.

Run:

```
python3 01\_fetch\_tickets.py
```

### `02\_load\_support\_tickets.sql`

Promotes `support\_ticket\_staging` into the permanent `support\_ticket` table:

* Matches each ticket to an existing customer by **email** and to a product by **SKU**, using the same `LEFT JOIN` + normalize-and-match approach built in Project 1 (so unmatched tickets still load rather than being dropped).
* Casts `resolution\_days`/`satisfaction\_score` from staging text to typed nullable columns, preserving the `NULL`-vs-absent distinction from step 1.

### Answer (API vs. file sources)

what was harder about the API (pagination, rate-limit handling, and fields that are conditionally present depending on ticket status, versus files where the full extract is available at once) and what breaks if the API is unavailable mid-run (the fetch script has nothing to read past the last successfully retrieved page, so any run interrupted by an outage needs to resume from that page rather than restart from page 1 — hence saving each page's raw response as it comes in).

## Part 2: Designing the Warehouse

### `03\_create\_dim\_date.sql`

Generates the date dimension **with SQL** (not typed in row by row), covering the full date range in the data: `Year`, `Quarter`, `Month`, `MonthName`, `DayOfWeek`.

### `04\_create\_warehouse\_schema.sql`

* Dimensions: `Dim\_Customer`, `Dim\_Product`, `Dim\_Date`.
* Facts: `Fact\_Review`, `Fact\_Ticket` — both reference the **same** three dimensions, which is what makes them conformed (item 5).
* All warehouse tables use **surrogate keys** (auto-increment IDs generated by the warehouse itself) rather than reusing the operational `customerid`/`productid`/etc.


NOTE: surrogate keys let the warehouse absorb changes on the operational side (an ID gets reused, a source system changes its own numbering, a second source system's ID collides with the first) without rewriting warehouse history, and they let `Fact\_Review` and `Fact\_Ticket` reference dimension rows uniformly even though the underlying source records don't share an ID scheme.

### Grain statements

* **`OrdersFact`:** one row = one combination of `Dim\_Customer`, `Dim\_Product`, and `Dim\_Date` — i.e., one order line.
* **`Fact\_Review`:** one row = one review, sourced from exactly one of `external\_reviews\_native`, `web\_feedback\_from\_json`, or `customer\_survey`, joined back to `Dim\_Customer`. Total: **132 rows** across all three sources.
* **`Fact\_Ticket`:** one row = one support ticket, referencing `Dim\_Product`, `Dim\_Customer`, and `Dim\_Date`.

### Conformed dimensions 

`Dim\_Customer`, `Dim\_Product`, and `Dim\_Date` are shared by both `Fact\_Review` and `Fact\_Ticket`. If each fact table had its own copy of, say, `Dim\_Product` instead, the same physical product could get two different surrogate keys in the two copies — breaking any cross-fact question ("do low-rated products also generate more tickets?") because the join would silently return no matches, or wrong ones if a key value happenedto collide.

### Side-by-side comparison 

Question: *What is the average rating by product category, per quarter?*

* **Project 1 normalized schema:** `reviews ⋈ products ⋈ Dim\_Date` — **3 joins**.
* **Star schema:** `Fact\_Review ⋈ Dim\_Product ⋈ Dim\_Date` — **3 joins**, same count, because the star schema mirrors the same relationships one level removed through surrogate keys. Both return the same result — the payoff of the star schema isn't fewer joins on this single query, it's that `Fact\_Review` and `Fact\_Ticket` can be asked the *same kind* of question against the *same* dimensions without redefining "product" or "quarter" twice.

Both queries are saved together in `05\_side\_by\_side\_queries.sql` for direct comparison.

## Part 3: Building the ETL

### `06\_run\_etl.sql`

1. **Dependency order (item 1):** dimensions load first, then facts — a fact row can't reference a dimension surrogate key that doesn't exist yet. Written as one repeatable script: `Dim\_Customer` → `Dim\_Product` → `Dim\_Date` → `Fact\_Review` → `Fact\_Ticket`.
2. **Unmatched rows (item 2):** the 12 Project 1 reviews with no matching customer are  pointed at a single **"Unknown" member** added to `Dim\_Customer`, rather than being dropped. Written answer, item **3.2**: dropping them would silently shrink the fact table below the true review count and break the Part 1/Project 1 reconciliation; routing them to "Unknown" keeps every review counted while still being explicit that
the customer link is missing, so anyone querying by customer can filter it out on purpose instead of it disappearing by accident.
3. Uses `ON DUPLICATE KEY UPDATE` on every fact insert (item 4) so the script is safe to re-run.

### `07\_reconciliation\_checks.sql` 

* `Fact\_Review` row count vs. the Project 1 `reviews`/combined-view row count — must match (132 either way).
* Average rating from `Fact\_Review` vs. the same average recomputed directly from the Project 1 operational tables — must match to the same decimal precision.
* Same pattern repeated for `Fact\_Ticket` against `support\_ticket`.

### `08\_rerun\_idempotency\_test.sql`  

Captures `SELECT COUNT(\*) FROM Fact\_Review` (and `Fact\_Ticket`) **before** running `06\_run\_etl.sql` a second time, runs it again, then captures the count **after**. Both counts must be identical — proving the `ON DUPLICATE KEY UPDATE` logic prevents double-loading.

### ETL vs. ELT  

This pipeline is **ETL**: staging tables hold raw, untyped data, and all transformation (matching customers by email, mapping SKUs to products, deciding "Unknown" for unmatched rows, generating surrogate keys) happens in the SQL that promotes staging rows into the warehouse — i.e., transformation happens **before** the row lands in its final fact/dimension table, not after.
